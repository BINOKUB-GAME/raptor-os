QUESTION 01 • CHOIX D'ARCHITECTURE

Pourquoi un socle OpenBSD monolithe en C natif plutôt que Linux avec Docker ?

Une stack de conteneurs empile un orchestrateur, un démon privilégié, des réseaux virtuels et des machines virtuelles applicatives qui élargissent la surface d'attaque et introduisent des latences imprévisibles (ramasse-miettes, surcouches réseau).

CENTURION privilégie le déterminisme : le système repose directement sur OpenBSD/amd64 (mitigations W^X, ASLR natif, LibreSSL) et exécute des passerelles transactionnelles compilées statiquement en C pur (raptor_db, raptor_db_post), isolées dans le chroot /var/www avec restriction stricte des appels système par pledge(2).

QUESTION 02 • VERROUILLAGE NOYAU

Comment administrer ou mettre à jour le bastion lorsque kern.securelevel=1 est actif ?

Lorsque kern.securelevel=1 est verrouillé, le noyau OpenBSD interdit à chaud toute modification des règles du pare-feu pf (pfctl -d ou pfctl -f sont refusés, même en root) ainsi que le retrait des drapeaux immuables (schg) sur les binaires critiques.

En exploitation courante, le défenseur conserve toutefois le plein contrôle de la table dynamique <badhosts> pour bannir ou lever une quarantaine sans redémarrer : 

raptor-os# pfctl -t badhosts -T show
raptor-os# pfctl -t badhosts -T delete 192.168.1.50

Pour une mise à jour majeure des règles /etc/pf.conf ou des binaires protégés par schg, il suffit d'effectuer un redémarrage planifié en mode maintenance (securelevel=0) avant de rebasculer en production verrouillée.

QUESTION 03 • BOUCLIER RÉSEAU & WAF

Comment fonctionne la fusion rap + pf et le bastion peut-il se bannir lui-même ?

Deux mécanismes complémentaires alimentent la table noyau <badhosts> (persistée dans /etc/pf.raptor_ban) : au niveau transport, les seuils overload <badhosts> flush global de /etc/pf.conf coupent immédiatement les rafales SSH (3/5s) et HTTP (50/5s) ; au niveau applicatif, RAPTOR-HTTPD/2.0 (raptor_ipc.c) injecte instantanément dans <badhosts> toute IP déclenchant une signature WAF TRAP_*.

Pour éviter toute paralysie du serveur par auto-bannissement, raptor_guard.c et raptor_ipc.c intègrent une liste blanche matérielle inconditionnelle qui exclut systématiquement les interfaces locales 127.0.0.1 et ::1 de toute action de quarantaine.

QUESTION 04 • COFFRE-FORT & FORENSIQUE

Comment les données sensibles sont-elles protégées contre une altération silencieuse ?

La base de données MariaDB écoute exclusivement sur l'interface de bouclage 127.0.0.1:3306, inaccessible depuis le réseau externe. À l'intérieur de la base raptor_db, la table piège raptor_vault_canary est gardée par le déclencheur SQL trg_raptor_canary_guard : toute tentative de lecture non autorisée ou de modification lève immédiatement l'exception RAPTOR_SQL_CANARY_BREACH interceptée par le démon raptor-sql-sentry.

En parallèle, rap sentry arm déploie des fichiers canaris dans /etc, /var/www, /home et /root, tandis que l'anneau mémoire partagé /raptor_blackbox conserve les 64 derniers événements critiques consultables hors-ligne via rap sentry blackbox.

QUESTION 05 • DÉPLOIEMENT MATÉRIEL

Que faut-il vérifier lors du premier démarrage après l'installation sur PC dédié ?

Lors de l'installation depuis la clé USB raptor-os-2.0-amd64.iso, assurez-vous que l'ensemble [X] site80.tgz est bien sélectionné. Au premier redémarrage, le script /install.site génère automatiquement des mots de passe MariaDB aléatoires uniques dans /root/RAPTOR_CREDENTIALS.txt.

Exécutez ensuite ces trois contrôles (et remplacez vio0 par le nom de votre carte réseau physique dans /etc/pf.conf si nécessaire) : 

raptor-os# ifconfig
raptor-os# rap status
raptor-os# rcctl check raptor mysqld raptor_sql_sentry slowcgi php85_fpm httpd
